# 実装チェックリスト

## 実装順序の原則

**ロジックを先に完成させ、絵がゼロの状態で通しプレイできるようにする。**

理由が3つある。

1. **絵は後からAI生成でハメ込む前提**なので、絵を待つと何も進まない
2. **数値バランス（H / P / D）は実際に遊ばないと決まらない。** 絵より先に遊べる状態が要る
3. `src/systems/` は Three.js を import しないので、**`node --test` で絵なしに検証できる**（設計書 §2）

したがって Phase 1 では、板ポリの代わりに **色付きの箱と DOM のテキスト**だけで全編を通せる状態を作る。

### つまずいた点と対処（記録）

1. **`fps 6` と表示された** → バグではない。**隠しタブでは Chrome が `requestAnimationFrame` を停止する**ため。同期的に `renderer.render()` を120回回して実測し、0.98 ms/frame を確認した。同じ理由で **CSS トランジションも隠しタブでは進行しない**ので、`getComputedStyle` で検証する際は `transition: none` を一時的に当てる必要がある

3. **壁が黒く沈んだ** → 自己遮蔽を疑ったが外れ。ピクセルを実測して**壁は床の半分の明るさになるのが物理的に正しい**と判明。起こし光（fill）の追加と、壁の地色を床より明るくすることで解決（設計書 §4.4.1 / プロンプト集 §6-6 に反映）

### Phase 1 で見つけた設計欠陥（テストが検出した）

**欠陥1（重大 / 修正済み）: 相方が絶対に折れなかった**
`P` 初期10・消耗1では、判断室4室で `10 → 6` しか減らず、`partnerBroken` に到達不能だった。
つまり「相方が折れる」機構（本作最大の設計問題の解）と、
「折れた相方は6室目の警告を出さない」という payoff が**両方とも死んでいた**。
→ `P` 初期 **8**・消耗 **2** に変更。譲らなければ5室目で必ず折れるようにした。
→ 副産物として **TrueEnd には「相方に一度は報酬を譲る」ことが必須**になった。

**欠陥2（修正済み）: 小物の初期所持が抜けていた**
ペンナイフ・懐中時計・眼鏡・マッチ箱を誰も持っていなかった。

**欠陥3（修正済み）: 復路に緊張がなかった**
往路を上手く進めたプレイヤーは、復路で一度も `D` を失わなかった。
原因は `H` が復路でまったく意味を持たないこと（`canRun` の0か正かでしか読まれず、減らない）。
そのため外套の「+3 H」に価値がなく、**衣裳室と銃器室が天秤として成立していなかった**。
→ **復路でも部屋ごとに `H -= 1 + floor(W/2)` を消費させた**（玄関は終点なので消費しない）。

**欠陥4（修正済み）: 犬を弔うと純粋に不利だった**
弔いは `H -2` を払うのに見返りがなく、しかも TrueEnd を遠ざけていた。
「情を選ぶと不利」は質問7-2で決めた思想と逆。
→ **弔った者は復路の初期距離 `D` が +1**（犬が近くにいる）。

### 修正後に確認できた挙動

| ルート | 結果 |
|---|---|
| 全服従 | 相方が5室目で折れ、小物ゼロ、障害を1つも解けず **追いつかれる** |
| 全拒否 | H 枯渇＋相方も折れ、支える代償で **追いつかれる** |
| 相方に早く大きく譲る（H が薄い） | **外套を拾わないと玄関で踏み込めない**（原作エンドまで） |
| 同上・外套を拾う | **TrueEnd**。走れない状態が続く方が高くつくので拾うのが正解 |
| 報酬配分を工夫（H が厚い） | **TrueEnd**。外套を拾うと逆に距離を1失う |
| 鉄砲を拾って撃つ | 距離を失い **追いつかれる**（純粋な罠として機能） |

**★外套は「罠」ではなく「条件付きの正解」になった。**
同じ選択肢の正解が、それまでの自分の選択によって反転する。純粋な罠より良い。

> **Phase 1 の完了条件は「絵がなくても面白いかどうかの見当がつくこと」。** 成果指標が「面白さ一本」である以上、ここで手応えがなければ絵を68枚描いても救えない。手応えがなければ Phase 2 に進まず、仕様書に戻る。

### Phase 2 で見つけた問題（すべて修正済み）

**問題1: build の並行実行で板が混線した**
`clear()` のあとに `await`（テクスチャ読み込み）が入るため、その間に別の build が
始まると「前の build が新しいグループに板を足す」状態になった。
実際に玄関の子が8個ではなく **14個**になり、山道の板が混ざった。
→ 各 build が自分のグループ参照を握り、現行でなければ何もしないようにした。

**問題2: DOM パネルが画面下42%を覆うので、構図を数値で決め直す必要があった**
役者の足元と接地影がパネルに隠れていた。各板を投影して NDC を測り、
`lookAt` を 1.6 → **1.2**、役者を z=-0.35 → **-1.8**、看板を y=2.1 → **1.6** にした。
パネルの `max-height` も 66% → **42%** に抑えた。
これは「勘で置く」と必ず外す種類の調整なので、**投影して測る**手順を残しておく。

**問題3: 復路のキー光が壁の裏側にあり、壁が完全に黒かった（`[1,1,1]`）**
壁は z=-4.5（法線 +z）と x=-4.5（法線 +x）にあるので、
キー光を `[-3, 6, -4]` に置くと壁の裏を照らすことになる。
→ **キー光は必ず x>0 かつ z>0 に置く**。`[2, 7, 4]` に変更。
実測値: 往路 奥壁`[13,7,2]` → 復路 奥壁`[13,3,2]`、左壁は `15` → `7`。
**明度は保ったまま色が赤へ振れ、左壁だけ落ちて非対称になる。**

**問題4: 山道の背景板が斜めに見えた**
z 軸に平行に置いていたため、固定カメラの方位（約40度）とずれていた。
→ 視線方向の奥に置き、カメラ方位に正対させた。

**問題5: `mountain/ground.png` が一覧に無かった**
山道の床として3D空間に敷く必要がある。アセットを **68 → 69枚**に更新した。

### 実装上の判断

**板テクスチャに文字を合成し、1枚の面にした。**
別の板を重ねる方式は z-fighting を起こし、ライティングも二重になる。
板のテクスチャはローダーのキャッシュが持つ共有物なので、**必ず新しい canvas に
板を写してから文字を載せる**。直接描くと他の部屋の看板まで汚染する。

**3D の看板は「実在感」のためであり、可読性は DOM パネルが担保している。**
同じ文面がパネルにも出るので、役者に一部が隠れても読めなくはならない。
だから役者との重なりを完全に消すために壁の外まで板を出す、といった無理はしない。

### Phase 3 で見つけた問題（修正済み）

**問題1（開発を止めていた）: Chrome が ES モジュールを古いまま使い続けていた**
`python3 -m http.server` は `Cache-Control` を送らないため、
Chrome が古いモジュールを再検証せずに使い続ける。
**配信ファイルは新しいのに、実行中のコードは古い**という状態になり、
自動検証が古いコードを検証していた（レイアウトを直したのに画面が変わらなかった）。
→ `scripts/serve.py` を追加。`no-store` を必ず付けて配信する。`npm run serve` はこれを使う。
→ **すでにキャッシュ済みのエントリはヘッダを直しても効かない**（ネットワークに出ないため）。
   その場合は**ポートを変えてオリジンを変える**のが最も確実。ポートは 8899 にした。

**問題2: 看板が CLOSE のカメラで上端が切れていた**
WIDE で測って収めても、CLOSE では拡大されて外に出る。
**構図は必ず WIDE と CLOSE の両方で測る。**
→ 看板を `y=1.2 / h=1.6` に、厨房の扉を `x=0.2 / h=2.4` に変更。

**問題3: 山道の背景板の空が画面外に出ていた**
下端を y=0 に接地させていたため。地平線がカメラの注視高さ付近に来るよう
`y=3.0 / 24x9` に変更した。

## フィードバック対応（第2回）

### 遷移の組み直し

- [x] **明転を遅くした** — 暗転 260ms / 明転 560ms（以前は両方220ms）。
      暗くするのは合図なので速くてよいが、明るくなるのが速いと切り替わった感じにならない
- [x] **フェードが終わるまで文字送りを始めない** — `onState` が「見せ終わるまでの Promise」を返し、
      `overlay` がそれを待ってから送りを始める。フェード中に送られると読めないまま流れていた
- [x] **建て替えとカメラのスナップを必ず真っ黒のあいだに終える** — 明転後にスナップしていたため画面が飛んでいた

### ★不具合: 厨房前で鍵穴を覗くと画面が壊れた

原因は2つ重なっていた。

1. `REVEAL:6 → RETURN:6` を「部屋の移動」と誤判定し、**振り返るだけの場面で退室の歩きが走っていた**
2. カメラのスナップを**明転のあと**に行っていたため、そこで画面が飛んでいた

→ **歩かせるのは「部屋番号そのものが変わるとき」だけ**にした。反転は同じ部屋なので歩かない。
→ 建て替えとスナップは暗転中に行うようにした。

### 看板のズームアップ

- [x] **寄っているあいだは役者を消す** — 対象とカメラのあいだに立って手前を塞いでいた。
      ★可視判定は `syncStage` に一本化した。`syncCamera` 側だけで消しても、
      あとから解決する `setActors` が上書きしてしまう
- [x] **寄っているあいだはテキスト枠を小さくする**（自動で `small`、31%）
- [x] **注視点を対象の中心より下に置く** — 画面中央に置くと下端がテキスト枠に隠れる

## フィードバック対応（第3回）

### テキストのページ送り（3件を1つの仕組みで解決）

指摘は3件あったが、原因は同じ「一度に全部流し込んでいる」ことだった。

- 各部屋で調べたときのコメントの直後に次のテキストが続いてしまう
- 相方と話す場面も同様
- エンディングの1回の表示量が長い

→ **ページ送りにした。**

- [x] 1ページは**スクロールなしで読める量**（4行目安。空行は 0.4 行として数える）
- [x] 送り終わると `▼` が点滅し、**枠のタップで次のページ**が出る
- [x] 読み終えたページは残るので、**さかのぼって読み返せる**（ログの確認）
- [x] 選択肢とチップは**最後のページを読み終えるまで出さない**
- [x] 結末の一覧も最後のページまで出さない
- [x] **ログ（いま起きたこと）と本文（いまの状況）は同じページに混ぜない**
      相方の台詞のすぐ下に看板の文面が続くと、台詞を読む区切りがなくなる
- [x] 最後のページを読み終えたら、いちばん下まで自動で送る（選択肢が出て枠が狭まるため）

### 場面ごとの文字送り速度

- [x] 玄関で扉が開かず泣く場面（`R1z`）は **15字/秒**。速いと情緒が流れてしまう
- [x] 結末は **24字/秒**、通常は **34字/秒**

### 表現の不具合

- [x] **「何も差し出さなかった」の違和感** — 小物だけを見て判定していたため、
      鉄砲を置いたのに何も渡していないように読めていた。
      **鉄砲や外套を描く文（obeyText）を先に出し**、小物は「〜も預けた」「〜だけは握り込んだ」にした
- [x] **S02 で犬が一疋しかいなかった** — 仮テクスチャが1体しか描いていなかった。
      原作は二疋なので、首輪と銀の笛つきで2体描くようにした
- [x] **相方が鉄砲を持っていなかった** — 原作の二人はどちらも猟銃を持っている。
      `hasGun` は二人ぶんを表す1つの旗なので、相方にも鉄砲の板を出すようにした

### 併せて直した潜在的な不具合

**`r_partner` で未知の選択IDが来ると、どの値でも「相方を置いていく」扱いになっていた。**
UI からは到達しないが、選択を既定値に落とす書き方は危険。
`r_partner` / `caught` / `r_final` はいずれも**選択を明示的に判定し、未知の id は無視する**ようにした。
