## 2. 最重要の設計原則: ロジックと描画の完全分離

**`src/systems/` は Three.js を一切 import しない。**

これにより `node --test` でブラウザなしにゲームロジック全体を検証できる。一方通行かつ周回前提のゲームで、**5種のエンディングすべてへの到達可能性を自動テストで保証**するために、この境界は絶対に破らない。

```
src/systems/*  ── 純粋関数のみ。three を知らない。テスト対象
      ↓ 状態オブジェクトを渡す
src/scenes/*   ── 進行制御。systems を呼び、render に描画を依頼
      ↓
src/render/*   ── Three.js。状態を受け取って絵にするだけ。状態を書き換えない
src/ui/*       ── DOM。会話と選択肢。選択結果を scenes に返すだけ
```

**依存の向きは一方通行。** `render` から `systems` を呼ばない。`systems` から `render` を呼ばない。

## 4. 2.5D ステージの構築方式

### 4.1 板ポリの配置

| 要素 | ジオメトリ | 姿勢 |
|---|---|---|
| 床 | `PlaneGeometry` | `rotation.x = -Math.PI / 2`（水平） |
| 壁 | `PlaneGeometry` | 垂直。部屋の奥・左・右に配置 |
| 家具・小物 | `PlaneGeometry` | 垂直。**カメラの向きに正対させる** |
| キャラ | `PlaneGeometry` | 垂直。**下端が `y = 0` に接するよう `position.y = height / 2`** |

**カメラは回転しない**（ズームのみ）ので、板を固定の向きでカメラに正対させれば破綻しない。動的なビルボード計算は不要。

### 4.2 接地 — チープさの最大の原因を潰す

キャラや家具が「浮いて見える」ことが、2Dゲームがチープに見える第一原因である。

```js
// billboard.js
mesh.castShadow = true;
mesh.material.alphaTest = 0.5;   // ★ 影を板の矩形ではなく絵の形にする
```

`alphaTest` を設定しないと、**影が長方形になる。** これは必ず設定する。

**r184 での注意点**（Phase 0 で実測）:
- `THREE.PCFSoftShadowMap` は**廃止済み**。指定するとコンソール警告が出て `PCFShadowMap` に差し替えられる。最初から `THREE.PCFShadowMap` を使う
- 影のバイアスは `shadow.bias` ではなく **`shadow.normalBias`**（0.03 前後）を使う。板ポリは光に対して斜入射になりやすく、`normalBias` の方が適している

さらに床に `receiveShadow = true` を設定し、`DirectionalLight` に `castShadow = true` と `shadowMap` を持たせる。

#### ★絵の画角は、板の姿勢ではなくカメラの姿勢で決める

固定カメラは **方位 40 度・水平から 22 度見下ろし**（`camera.js` の `SHOT.WIDE`）。
垂直の板に貼った絵は、この角度から見た絵でなければ場面と噛み合わない。

`prop` レシピは全アセットに `viewed straight from the front, perfectly head-on` を課していた。
背の高いもの（扉・鏡・外套掛け）は 0 度と 22 度の差が小さいので成立するが、
**腰より低いもの**はカメラに天面が見える。立面図（天面のない矩形）を垂直の板に貼ると
「床に貼ったシール」になる。衣裳室の靴置きが実際にそうなっていた。

**★板を少し倒して逃げようとして失敗した。**
`rx` で 0.5rad 倒し、方位も正対から外してみたが、**垂直のままより悪くなった**。
立面図の絵に角度だけ付けても、絵の中の遠近（無い）と場面の遠近が噛み合わないので、
「傾いた紙」になるだけである。姿勢をいじって絵の画角を代替することはできない。

正解は**絵の側をカメラの角度で描き直す**こと。レシピを3つに分ける。

| レシピ | 対象 | 画角 | 板の姿勢 |
|---|---|---|---|
| `prop` | 腰より高いもの | 真正面（head-on） | 垂直・カメラ正対 |
| `prop_low` | 腰より低い床置き | **水平から22度・方位40度**の見下ろし三分の四視 | 垂直・カメラ正対 |
| `prop_flat` | 敷物・床に落ちた布 | **真上から**（top-down） | **床と同じ水平面に寝かせる** |

`prop_low` の画角は「三分の四視で」と曖昧に書かず**角度を数字で固定する**。
曖昧に書くと生成ごとに角度が変わり、同じ部屋の中で家具ごとに視点がばらつく。

`prop_low` は照明指定から `no perspective distortion` を外す（`FLAT_ANGLED`）。
角度を付けて描かせるのに「遠近を付けるな」と併記すると矛盾したプロンプトになる。
排したいのは広角レンズの歪みだけなので、そう書く。

#### ★寝かせる板（`flat: true`）

敷物は立て板ではない。床と同じ水平面に貼る。玄関のマットは絵が**元から真上視**なのに
垂直の板に貼っていたため、敷物が立て看板のように立っていた（絵は作り直さなくてよかった）。

```js
{ tex: '.../mat.png', x: -3.4, z: -1.0, w: 1.8, h: 1.0, flat: true, ry: -Math.PI / 2 },
```

`stage.js` の `pose()` が寝かせる。実装で守ること:

- 回転の順序は **`'YXZ'`**。既定の `'XYZ'` は X が世界軸で先に効くので、方位を持つ板がねじれる（`seam.js` で同じ罠を踏んでいる）
- `y` をわずかに浮かせる（`FLAT_LIFT = 0.012`）。床と同一面だと z-fighting する
- **影を落とさない**。床と同一面なので、影が絵の真横にずれて二重に見える
- **影は受ける**（`receiveShadow`）。寝かせた板は床の続きなので、役者の影が落ちないと浮く
- 置き場所は扉の前。**床の中央に置くとただの染みに見えた**

★`layout.js` に「好きな角度で倒す」口は開けていない。中途半端に倒した板は
垂直のままより悪くなるので、選べるのは「立てる」か「寝かせる」の二択だけにする。

### 4.3 カメラ

```js
// camera.js
export const SHOT = {
  WIDE:  { pos: [4.8, 4.2, 5.8], look: [0, 1.2, 0] },
  CLOSE: { pos: [3.7, 3.3, 4.5], look: [0, 1.2, 0] },
};
```

**★構図は必ず WIDE と CLOSE の両方で測る。** WIDE で収めても CLOSE では拡大されて画面外に出る（Phase 3 で看板の上端が切れた）。

**注視点 1.2 は勘ではなく実測で決めた値。** DOM のパネルが画面下 42% を覆うため、
各板を投影して NDC を測り、主題がパネルの上に収まる位置を選んでいる。
注視点を上げると役者が隠れ、下げすぎると壁の看板が画面外に出る。
**レイアウトを触ったら必ず投影して測り直す。**

**`OrthographicCamera` ではなく、FOV を絞った `PerspectiveCamera` を使う。**
完全な平行投影は「立体感が出ない」＝あなたが最も避けたいチープさに近い。FOV 28 程度のわずかな遠近が、アイソメの見た目を保ちつつ奥行きを感じさせる。

**決断の瞬間の寄り**（仕様書 §4.2 [4]）は、`camera.position` と `lookAt` を補間するだけで実現する。**アセット追加はゼロ。**

### 4.4 ライティング — 往路と復路の反転をここで作る

**★キー光は必ず x>0 かつ z>0 に置く。** 壁は z=-4.5（法線 +z）と x=-4.5（法線 +x）
にあるので、マイナス側に置くと壁の裏を照らすことになり、カメラに向いた面が
完全に黒くなる（Phase 2 で実際にそうなった）。

```js
// lighting.js
export const PRESET = {
  OUTBOUND: {   // 往路: 上品な西洋料理店
    ambient: 0x3a3026, ambientIntensity: 0.8,
    key: 0xffd9a0, keyIntensity: 1.2, keyPos: [4, 8, 3],
    fill: 0x8a7a5c, fillIntensity: 0.75, fillPos: [5, 3, 6],   // 影を落とさない起こし光
    fog: { color: 0x2a2218, near: 10, far: 34 },
  },
  RETURN: {     // 復路: 同じ部屋が下ごしらえの現場に見える
    ambient: 0x1c2230, ambientIntensity: 0.5,
    key: 0xff6a4a, keyIntensity: 0.9, keyPos: [-3, 6, -4],
    fill: 0x3d4a63, fillIntensity: 0.45, fillPos: [5, 3, 6],
    fog: { color: 0x120e10, near: 6, far: 22 },
  },
};
```

**同じテクスチャ、同じ3Dシーン、ライトのプリセットを差し替えるだけで意味が反転する。** 復路のために新しい部屋を作る必要はない。追加テクスチャは小物（床に置かれた鉄砲・外套）のみ。

### 4.4.1 起こし光（fill）が必須である理由 — Phase 0 の実測結果

キー光だけを置くと、**壁が背景として読めなくなる。**

Phase 0 でレンダーターゲットからピクセルを読んで実測した結果:

| 面 | 線形値 |
|---|---|
| 床 | `[14, 7, 2]` |
| 壁 | `[7, 4, 1]` |

**壁は床のちょうど半分の明るさになる。** これはバグではなく物理的に正しい。キー光が上から来るため、法線が上を向いた水平面（床）が有利になる。

対策は2つ。両方やる。

1. **カメラ側から `fill`（影を落とさない起こし光）を当てる**
2. **壁のテクスチャを床より明るく生成する**（プロンプト集 §6 の運用ルールに反映済み）

2 を怠ると、AI生成した壁がどれも黒く沈み、「暗くてよく見えないゲーム」になる。

### 4.5 色調の統一 — AI生成のばらつきを吸収する

AI画像生成は生成ごとに絵柄・彩度・光がズレる。**これを実行時に上塗りして統一する。**

```js
// grading.js
renderer.toneMapping = THREE.ACESFilmicToneMapping;
renderer.toneMappingExposure = 1.0;
scene.fog = new THREE.Fog(preset.fog.color, preset.fog.near, preset.fog.far);
```

加えて canvas 要素に CSS フィルタを掛ける（最も安価な手段）。

```css
#stage { filter: saturate(0.85) contrast(1.05); }
```

**共通のライト・共通のフォグ・共通のトーンマッピングを通すことが、68枚のばらつきに対する最大の防御になる。** これは2D実装では画像を1枚ずつ手で調整しなければ得られない効果である。

### 4.6 境目を消す（地面と背景板）

板ポリを突き合わせると境目が剃刀のような直線になる。これが
「3D空間にテクスチャを貼っただけ」に見える最大の原因で、タイトル画面で特に目立つ。

★**隠すべき線は「地面板の縁」ではなかった。**
背景板は地面板を貫いて立っているので、**交わったところに直線が1本**できる。
板の縁は画面の左右で見えていただけで、地面を広げれば背景板の裏に隠れる。
そこで地面板を 14 → **24** に広げた（枡の大きさは変えないようタイル数も 4 → 7）。
これで隠すべき境目は交線1本だけになる。

そのうえで2つ重ねる。片方だけでは足りない。

1. **接触の影**（`render/seam.js`、絵は使わない）
   交線の**両側**を暗くする。地面の側だけ暗くすると、線の向こうが明るい背景板のままで
   帯が一本の縞に見える。線をまたいで暗さが連続すると影が溜まって見える。
   勾配は濃い側を急に、薄い側をゆっくり抜く（直線的に抜くと帯の上端がまた線になる）。
2. **草の帯**（`mountain/grass_edge.png`）
   交線に立てる横長の枯れ草。**不規則なシルエットで直線を壊す**。
   下半分は密（線を隠す）、上は疎に抜ける（壁に見せない）。高さは 1.2
   ——役者が 2.2 なので、これ以上高いと生垣に見える。

採らなかったもの。
- **SSAO などの後処理** … 板が3枚しかないので遮蔽が出ない。画面空間の陰影を
  水彩＋線画に掛けると灰色に濁る。費用に対して効果が薄い
- **ライトベイク** … 焼く工程がない（ビルド工程を持たないのが前提）
- **ノーマルマップ** … 70枚ぶんの法線が必要で、しかも凹凸が出ると
  「平面に描いた絵」という画作りが崩れる
- **ほこり・霧のパーティクル** … 霧は `scene.fog` で入っている。粒を漂わせても
  直線は消えない。止まった画に動くノイズを足すだけになる
- **高さブレンドのシェーダー** … 床と壁は別メッシュなので混ぜられない。
  実装すると結局 1 と同じ「境目に半透明の帯を置く」ことになる

★**部屋（床↔壁）には入れていない。** 実機で見て違和感がなかったので、
効果の薄いところに描画を増やさない。必要になったら `seamStrip()` を呼ぶだけで足りる。

#### 板を寝かせるときは回転の順番に注意する

`rotation.set(-PI/2, azimuth, 0)` は既定の 'XYZ' だと
「先に方位、あとで倒す」の順に効くので、水平にしたい板が斜めの面になる
（実機で楔形の影が出た）。`rotation.order = 'YXZ'` にして、
倒してから方位を向ける。

## 5. マゼンタ背景の透過処理

AI画像生成は透過PNGを安定して出せないため、**マゼンタ（`#FF00FF`）背景で生成する**（プロンプト集 §TECH_SPEC）。

ビルド工程がないため、**実行時にブラウザで抜く。**

```js
// chromaKey.js
export async function loadKeyed(url, key = [255, 0, 255], tol = 40) {
  const img = await loadImage(url);
  const cv = document.createElement('canvas');
  cv.width = img.width; cv.height = img.height;
  const ctx = cv.getContext('2d', { willReadFrequently: true });
  ctx.drawImage(img, 0, 0);
  const d = ctx.getImageData(0, 0, cv.width, cv.height);
  const p = d.data;
  for (let i = 0; i < p.length; i += 4) {
    if (Math.abs(p[i] - key[0]) < tol &&
        Math.abs(p[i+1] - key[1]) < tol &&
        Math.abs(p[i+2] - key[2]) < tol) {
      p[i+3] = 0;
    }
  }
  ctx.putImageData(d, 0, 0);
  const tex = new THREE.CanvasTexture(cv);
  tex.colorSpace = THREE.SRGBColorSpace;
  return tex;
}
```

### 5.1 アセットの出典は `src/data/assets.js` だけ

**`docs/プロンプト集.md` と `docs/アセット一覧.md` は生成物。** `npm run gen:docs` で作り直す。

散文のドキュメントとコードを二重管理すると必ずずれる。実際に、コードが使う6枚が一覧から漏れ、
看板の板を6部屋ぶん別アセットとして数えていた（実際は1枚を共有すれば足りる）。

`assets.js` の **レシピ**が画角と技術指定の両方を決めるので、
`STYLE_BASE ＋ 対象 ＋ レシピ` を連結すれば、**判断の余地なく完成したプロンプトになる。**

> **★「全画像共通の TECH_SPEC」という設計は誤りだった。**
> 床・壁・背景は板いっぱいに貼る「面」なので、マゼンタ背景と `isolated subject` を
> 指定してはいけない。共通ブロックにこれを入れると、使う側が読み替えを強いられ、
> 機械的に生成できなくなる。レシピを分けるのが正しい。

`test/assets.test.mjs` が以下を検証する。

- コードが参照するアセットがすべて `assets.js` に載っている
- `wired: false` でないアセットが実際にコードから参照されている
- **面のレシピにマゼンタ背景が混ざっていない**
- 完成プロンプトに矛盾した指定がない（面に `isolated subject`、床に `tileable` 欠落など）

### 5.2 ★生成した絵のばらつきは、板の側で吸収する

AI画像生成は、指定しても**縦横比を守らないし、拡張子が .png でも中身は JPEG のことがある。**
そこを人手で直させると制作が止まるので、コードで吸収する。

| ばらつき | どう吸収するか | どこ |
|---|---|---|
| 余白が多い／比が違う（抜き板） | マゼンタを抜いたあと、**不透明部分に切り詰めて**から絵の比で板を作る | `chromaKey.trim()` ＋ `makeBillboard({fit})` |
| 比が違う（壁） | はみ出す方を切り落として中央を使う（cover） | `makeWall()` |
| 比が違う（床） | 繰り返し数を絵の比で割り戻し、タイルを正方形に見せる | `makeFloor()` |
| 継ぎ目が合わない（床） | **鏡張り**（`MirroredRepeatWrapping`）で敷く。隣の枡が反転するので継ぎ目は必ず一致する | `makeFloor({mirror})` |
| 中身が JPEG | `createImageBitmap` が中身で判断するのでそのまま読める | `fetchBitmap()` |
| JPEG の境界の滲み | 二段の閾値で羽を付け、縁に残る紫を中和する | `chromaKey.keyOut()` |

**吸収できないもの**は2つだけ。

- **マゼンタ背景がない抜き板** — 抜けない。作り直すしかない
- **向きのある床の継ぎ目** — 板張りや市松は鏡張りにすると反転が見えるので、絵の側で合わせるしかない
  （地面のように向きのない絵なら `mirror: true` で解決する）

### 5.3 鏡張りをどこに使うか

| 絵 | 鏡張り | 理由 |
|---|---|---|
| `mountain/ground.png` 土・草 | **使う** | 不規則で向きがない。反転しても分からない |
| `common/floor_wood.png` 板張り | 使わない | 板の向きが反転して V 字の折り返しが出る |
| `common/floor_tile.png` 市松 | 使わない | 直線の格子が反転で崩れる |

指定はアセット側（`assets.js` の `mirror: true`）。描画側で判断しない。

`npm run check:assets` が、投入した絵をこの基準で判定する。

### 5.4 ローダーの優先順位（3段フォールバック）

1. `assets/textures/<path>` が存在すれば、それをそのまま使う（手作業で作った高品質な透過PNG）
2. なければ `assets/raw/<path>` を使う。**抜き板だけ**実行時クロマキーで抜く
   （面＝床・壁・背景は抜かない。`chromaKey.js` の `SURFACE` で判定）
3. どちらも無ければ **仮テクスチャ**を返す（`render/placeholder.js`。ファイル名を描き込む）

**3段目が決定的に重要。** 69枚が1枚も存在しない状態から Phase 2〜4 を進められる。
実物が `assets/` に置かれた瞬間、ローダーが自動でそちらを使う。
未生成の枚数は画面左上に出るので、制作の進捗がそのまま見える。

存在確認は `fetch` で行う（`Image` の `onerror` に頼ると 404 がコンソールを埋める）。

### 5.5 ★ImageBitmap を CanvasTexture にそのまま渡さない

`createImageBitmap()` で得た `ImageBitmap` は、three の `flipY` が効かない（GPU へ上げる際の
`UNPACK_FLIP_Y_WEBGL` が ImageBitmap には適用されない。three 側の既知の制約）。
既定の `flipY = true` を信じて渡すと、**貼った絵が上下逆さまになる。**

抜き板は `keyOut()` / `trim()` が canvas を返すので無事だった。
面（床・壁・背景・一枚絵）だけが生の ImageBitmap を渡していたため、
**山道の背景が上下反転し、山猫軒が逆さに立っていた**（結末の一枚絵も同じ経路）。
床と壁は模様が上下でほとんど変わらないので、誰も気づけなかった。

`toTexture()` が ImageBitmap を canvas に写してから渡す。1回だけの処理で、結果はキャッシュされる。

床・壁で「上下どちらが見えるか」も変わる点に注意。壁は 9 の高さのうち
奥壁で画面に入るのは y=2.63 までなので、**絵の下端（腰壁・幅木の側）が映る。**

## 6. 看板の描画 — Canvas 2D → テクスチャ → 板ポリ

**看板の文字を AI 生成画像に含めることは禁止。** AI画像生成は日本語の文字をまともに描けない（崩れた漢字、存在しない字形）。しかも生成し直すたびに変わる。

```js
// signboard.js
export function makeSign(lines, opt = {}) {
  const cv = document.createElement('canvas');
  cv.width = 512; cv.height = 1024;
  const ctx = cv.getContext('2d');
  // 板の地色（AI生成の板テクスチャに重ねる場合は透明にする）
  ctx.font = `${opt.size ?? 34}px "Yu Mincho", "Hiragino Mincho ProN", serif`;
  ctx.fillStyle = opt.color ?? '#241a12';
  drawVertical(ctx, lines, cv.width, opt);   // 縦書き: 1文字ずつ配置
  const tex = new THREE.CanvasTexture(cv);
  tex.colorSpace = THREE.SRGBColorSpace;
  return tex;
}
```

### 6.1 なぜ看板だけ3D空間に置くのか

仕様書 §7 の最重要カット——**塩の看板を読み、鍵穴に眼玉がある**。この瞬間、**看板と鍵穴は同じ空間に、同じ光の下にある必要がある。** 看板が DOM で画面に浮いていたら「その扉に書かれている」という実感が消え、鍵穴との関係が切れる。

**このゲームで最も重要な1カットが、実装方式ひとつで死ぬ。**

### 6.2 縦書き
大正期の看板は縦書きが自然。Canvas 2D に縦書き API はないため、`drawVertical()` で1文字ずつ配置する。列は右から左へ、字は上から下へ。

| 字種 | 処理 |
|---|---|
| `ー〜―─（）「」『』〔〕【】〈〉《》…‥：；` | **90度回転** |
| `、。，．` | 右上へ寄せる |
| `ぁぃぅぇぉゃゅょっ` などの小書き | わずかに右上へ |

### 6.2.1 ★書ける面は絵から探す。割合で決め打ちしない

文字を置く枠を「画像の 16%〜84%」のように決め打ちしてはいけない。
板の絵は AI 生成で、こちらが頼まなくても**吊り鎖・彫りの枠・支柱**まで一緒に描いてくる。
決め打ちの枠は鎖の上や枠の外に文字を置く（実際に玄関の看板がそうなっていた）。

`findPanel()` が絵から書字面を探す。この絵柄では書字面は
「まわりより明るい無地の矩形」で必ずあるので、明るい画素の**行と列の連続**を見れば足りる。
見つからなければ画像全体の少し内側へ落とす（枠のない板でも壊れない）。

生成側の条件は `assets.js` の `sign` レシピに入れてある
（**書字面は板の縦横3/4以上を占める、枠より明るい無地の矩形**）。
これは人の判断を要求しない条件なので、プロンプト集にそのまま乗る。

#### ★「明るい割合」は必ず**探している範囲の中**で数える

行・列の連続を拾うとき、明るい画素の割合を**反対側の全長**に対して数えてはいけない。
書字面が板の半分ほどの高さしかないと、面の**内側の列**でも
「明るい行 24 / 板の全 48 行」でちょうど 50% の境目に乗り、
通るか落ちるかが画素のゆらぎで決まる。

実際に 807×831 の板から **252×338（板の 31%）** しか拾えず、
字が本来の 4割の大きさになり、しかも面の右下に寄って描かれていた
（「看板の字が小さい」という指摘の原因はここ。板の寸法でも字詰めでもなかった）。

**行 → 列 → 行**と絞り込む。1回目は板の全幅で行を拾い（面は板に対して十分横に広い）、
2回目はその行の中だけで列を数え、3回目は絞った列で行を取り直す。
2回目以降は割合の分母が面自身の寸法になるので、判定が意味を持つ。

### 6.2.2 ★文面は面の形に合わせて折り返す

1文＝1列に固定すると、面の形と文面の長さが噛み合わない。
15字2列の文面を横長の板に置くと、字は高さで決まる小ささのまま板の中央に細く浮く。
`layout()` が折り返す位置を 2字〜最長まで試し、**字が一番大きくなる割り方**を選ぶ。
句読点は前の列に残す（行頭禁則）。

これで板の縦横比と文面の長さの対応表が要らなくなる。
どちらが変わっても、もう片方を直さなくてよい。

### 6.3 板テクスチャへの合成

**板のテクスチャはローダーのキャッシュが持つ共有物。** そこへ直接描くと他の部屋の看板まで汚染する。`composeSign()` は必ず新しい canvas に板を写してから文字を載せる。

別の板を重ねる方式は採らない。同一平面で z-fighting を起こし、ライティングも二重になる。

### 6.3.1 ★奥壁に置ける高さは 2.63 しかない

カメラが俯瞰なので、奥（z=-4.25）は上がすぐ画面外へ出る。
**奥壁で画面に入るのは y=2.63 まで。** 役者の背丈は 2.2。

つまり扉の板を大きくしても開口は高くならない。冠や梁を描き足した絵は、
板を画面いっぱいにしても開口が 1.8 しか取れず、**人が通れない扉**に見える。
開口を高くするのは寸法ではなく絵の役目なので、
`door_frame.png` のプロンプトに「開口が画像の縦9割」を条件として入れてある。

壁掛けの板も、中心 y に高さの半分を足した値が 2.63 を超えると上が切れる
（鹿の首の角が切れていた）。

### 6.4 3D の看板の役割
**「実在感」のためであり、可読性は DOM パネルが担保している。** 同じ文面がパネルにも出るので、役者に一部が隠れても読めなくはならない。役者との重なりを完全に消すために板を壁の外まで出す、といった無理はしない。

## 7. UI（DOM オーバーレイ）

会話文・選択肢・エンディング文は **DOM** で描く。読みやすさが最優先で、日本語フォントの自由度・行送り・禁則処理をブラウザに任せられる。

```
#stage        <canvas>   Three.js の描画先
#overlay      <div>      会話・選択肢（pointer-events: auto）
#vignette     <div>      H に応じた周縁の暗さ（pointer-events: none）
```

### 7.1 ゲージの表示 — 数値を出さない

| 対象 | 実装 |
|---|---|
| H（空腹） | `#vignette` の `box-shadow: inset` の強さ ＋ カメラの微小な揺れ（5段階） |
| P（相方の限界） | **台詞**（`dialogue.js` のテーブルから段階で選択）＋ 表情差分テクスチャ |
| W（重量） | 立ち絵の服装段階 ＋ 鉄砲レイヤーの有無（**見えている**） |
| D（追跡） | 部屋に伸びる影の長さ（`DirectionalLight` の角度で表現） |

**数値・バー・パーセントを画面に出してはならない。** プレイヤーが最適化を始めた瞬間、山猫軒は表計算ソフトになる。

## 8. 入力

```js
// input.js
el.addEventListener('pointerdown', onPointerDown);
```

`touchstart` は使わない。`pointerdown` の統一でマウス・タッチ・ペンが同一コードで動く（Demo_5・Demo_7 と同じ方式）。

**スマホでは縦持ちを検知して案内を数秒だけ出す。★止めてはいけない。**

アイソメのジオラマは縦構図では成立しないので横向きを薦める。ただし **iOS には画面の向きのロックがある。**
ロックしている端末は倒しても `innerHeight > innerWidth` のままなので、ここで進行を止めると
**プレイヤーの側に外す手立てがない壁**になる（実際に「画面が一向に動かない」報告が出た）。

- 案内は `#rotate-notice` に `.shown` を付けて出し、`ROTATE_NOTICE_MS`（3.8秒）で自分から消える
- `pointer-events: none`。案内が出ている間もタップは下の枠に届く
- 出すのは**横→縦に変わった瞬間だけ**。`resize` は URL バーの伸縮でも何度も来るので、
  直前の向きを覚えておかないと消えた案内が出続ける
- 文面も「〜してください」（命令）から「横向きにすると画面全体が見えます／そのままでも遊べます」に変える。
  遊べないと読ませてはいけない

縦持ちの表示そのものを整えることはしない（アイソメの構図が縦では成立しないため、
そこに手を入れるのは労力の置き場所を間違えている）。**止めないことだけが要件である。**

## 11. 演出の方針（フィードバック対応で固めたもの）

| 何を | どう見せるか | なぜ |
|---|---|---|
| **部屋番号が変わった** | 出口の扉まで歩く → 扉をくぐる → 暗転 → 建て替え → 明転 | 暗転だけでは「移動した」感じが出ない |
| 場所は変わるが部屋は同じ（反転） | **歩かせない。** 暗転と建て替えだけ | 振り返るだけの場面で退室すると画面が壊れる |
| 同じ部屋で判断に進む | 暗転しない。カメラだけ寄る | 一手ごとに暗転するとうるさい |
| 何かを調べた | 対象に寄る。**役者を消し、テキスト枠を小さくする** | 役者が手前を塞ぎ、枠が対象を隠す |
| 相方を捨てるか決める | 照明 `MOMENT` ＋ 彩度を落とす ＋ 相方に寄る | 他の場面と同じ見た目では臨場感が出ない |
| 待機中 | 呼吸と微かな揺れ。**足元は床に残す** | 微動だにしないと人形に見える |
| 小物の渡す／隠す | チップの色で明示 | テキストの変化だけでは選んだか分からない |

**主人公は無言なので、感情は身体の描写で書く。** 「悲しかった」と書かず、掌に残った指の跡を書く。

**服従の描写は「大きいもの → 小物」の順で書く。** 小物だけを見て「何も差し出さなかった」と書くと、鉄砲を置いたのに何も渡していないように読めてしまう。

**選択の分岐は既定値に落とさない。** `if (id === 'support') {...} else {置いていく}` のように書くと、未知の id が来たときに相方を勝手に見捨てることになる。必ず明示的に判定し、未知の id は無視する。

**エンディングは「直後の描写 → 時間の経過 → 余韻」の三段で書く。** 原文の引用で終わると何が起きたのか伝わらない。

### 11.1 遷移の順序（守るべき規則）

```
（部屋が変わるときだけ）扉まで歩く → 扉をくぐる
  ↓
暗転 260ms
  ↓  ★ここで建て替えとカメラのスナップを済ませる
  ↓    明転後にスナップすると、そこで画面が飛ぶ
明転 560ms
  ↓
文字送り開始   ★フェード中に送ると読めないまま流れる
```

`onState` は「見せ終わるまでの Promise」を返し、`overlay` がそれを待ってから送りを始める。

### 11.1.1 テキストはページ送りにする

一度に全部流し込むと、最初の行を読む余裕がないまま次が出てしまう。

| 決めごと | 内容 |
|---|---|
| 1ページの量 | スクロールなしで読める量（4行目安。空行は 0.4 行） |
| 次へ進む | 枠をタップ。送り中のタップは「残りを即座に出す」 |
| 読み終えたページ | 残す（さかのぼって読み返せる） |
| 選択肢・チップ・結末の一覧 | **最後のページを読み終えるまで出さない** |
| ログと本文 | **同じページに混ぜない**（台詞を読む区切りが消える） |
| 送りの速さ | 通常 34字/秒／結末 24／玄関で泣く場面 15 |

速さは `view().speed` が場面ごとに返す。情緒を出したい場面だけ遅くする。

### 11.1.2 一枚絵のカット（鍵穴の眼玉・結末）

部屋を消して、カメラの正面いっぱいに板を1枚置く（`fullFrameAt(dist)`）。

★**視線に垂直な面**にするのが要点。垂直な壁として置くと、カメラが俯瞰で傾いている
ぶん画角の計算が合わず、絵の中央だけが写る（実際にそうなった。結末の5枚すべてで
起きていて、眼玉のカットを作るまで気づかなかった）。
視線に正対させれば `2*dist*tan(fov/2)` がそのまま使える。

寄る演出は**暗転より先**に動かす。寄る対象は「まだ建っている前の部屋」の板なので、
建て替えのあとでは消えている。

#### 鍵穴のカットは2枚に分けて溶かす

1枚絵で「暗闇に眼玉」を出すより、**扉を見せてから溶かして眼玉に変える**ほうが怖い。

```
V6e  eyes   扉の一枚絵。かぎ穴は黒く、まだ何もいない  → 「かぎ穴に目を近づける」
V6f  eyes2  扉が溶けて、その黒からそのまま眼玉が現れる → 「目をそらす」
```

要点が3つある。

1. **覗きこむのはプレイヤーの意思にする。** 店の指示で覗くのではなく、自分で近づいた
   から目が合う。この順序でないと怖くならないので、`eyes` で一度手を止める。
2. **位置合わせをしない。** 扉の絵に眼玉の板を重ねて座標を合わせる案は捨てた。
   かぎ穴の位置は生成された絵ごとに動くので、決め打ちすると必ずずれる。
   同じ画角の2枚をクロスディゾルブすれば合わせる必要がない。
   かぎ穴の黒と眼玉の背景の黒が同じなので、**そこが眼になったように見える**。
3. **溶けたあとも止めない。** 眼玉の板をごく遅く（毎秒 0.6%、上限 13%）近づけ続ける。
   読んでいるあいだに間合いが詰まるので、落ち着いて読めない。

2枚は `scene`（面）として扱う。マゼンタを抜かず、切り詰めもしない
——切り詰めると2枚で切る量が変わり、溶け目が動く。
画角には**収めず切り取る**（`cover`）。縁まで絵なので、収めると余白が出る。

板は建て直さない。`eyes → eyes2` で同じ板を使い続けるので、
`buildKeyholeCut()` は鍵で2回目を弾く。`placeKey()` も両方 `'EYES'` を返す
——ここで場所が変わると暗転が挟まり、溶けて入れ替わるのが見えなくなる。

### 11.1.3 寄りの距離は画角から逆算する

対象の高さに係数を掛けて距離を決めてはいけない。
`dist = 高さ * 2.9` としていたので対象が画面の 69% を占め、
テキスト枠が覆う 45% を引いた 55% に収まらず、**ほとんどの「調べる」で対象が枠外に出ていた。**
幅は見ていなかったので、横長の板は左右にもはみ出していた。

```
距離 d での見える高さ 2H = 2*d*tan(fov/2)
枠の上に残る帯         = 2H*(1-PANEL_COVER)
d = max(高さ/(2*tan*FIT*(1-PANEL_COVER)), 幅/(2*tan*ASPECT*FIT))
```

そのうえで、カメラと注視点を**同じベクトルだけ**真下へずらして対象を帯の中央へ上げる。
両方を同じだけ動かすので向きは変わらない（固定カメラの文法を壊さない）。
`PANEL_COVER` は style.css の `.panel` の高さと対で決めている。

### 11.1.4 寄りを解くのは「読み終えたとき」

以前は次の選択肢を押すまで寄ったままだった。読み終わっているのに画面が対象に
張りついていると、進行が止まって見える。テキスト枠を押した時点で引きに戻す
（`onFocusEnd`）。

このとき役者を建て直せるように、`setActors()` は**見えないときも板を建てる**。
早期 return していたので、`setActorsVisible(true)` を呼んでも中身が空で
二人が戻ってこなかった。

### 11.1.5 同じ本文を二度送らない

部屋の本文（部屋名と看板の文面）は、その部屋にいるあいだ変わらない。
選択肢を押すたびに送り直していたので、**4択なら同じ文が4回流れていた。**

変わっていない本文は「残したまま、送らずに出す」。消してはいけない
（看板はこのゲームの謎そのものなので、読み返せなくなる）。
送るのは「いま起きたこと」＝ログだけ。

並び順は古いものが上、新しいものが下にする。
部屋に入った直後は ログ→本文、本文が据え置きのときは 本文→ログ。
固定にすると、送り終わりに下へスクロールしたとき新しい行が画面外に残る。

### 11.1.6 テキスト枠は内容で伸縮させない

文章の量や選択肢の数で高さを変えていたので、一手ごとに枠が動いて落ち着かなかった。
高さは固定し、あふれる文章は枠の中で送る。
高さが変わるのは3つだけ ——
遊ぶ人が畳んだとき / 結末（3Dを隠すものがなく文章が長い）/ 鍵穴の眼玉の一枚絵
（絵が主役。暗転を挟んで入るので枠が動いて見えない）。

### 11.1.7 相方の肖像は喋ったときだけ出す

出しっぱなしにすると、棚や鏡を調べているあいだも顔が並び、
顔は「そこにいる」以上のことを何も伝えなくなる。
喋ったときだけ出せば、**顔が出たこと自体が合図**になる。
判定は `partnerSpeaks()`。台詞をログに積んだ側（`choose()`）が旗を立てる。

### 11.1.8 板を浮かせると影だけが残る

`y` を明示すると板は宙に浮く。0.3 浮かせただけで、地面の影が足元から離れて見える
（山道の門の札で実際に起きた）。床に立つものは `y` を書かない（下端が y=0 に接地する）。

壁に掛けるものは、壁から離すほど影が壁の上を大きくずれる。
光は `[4,8,3]` から来るので、0.2 離すと影は 0.53 下・0.27 横にずれ、はっきり浮いて見える。
`ON_WALL_Z / ON_WALL_X = ±4.44`（壁から 0.06）まで寄せる。

絵に台座が描かれているもの（`wall_lamp.png` は壁付け燭台ではなく脚付きランプだった）は、
そもそも壁に掛けてはいけない。床に立てる。

### 11.1.9 ★ログは「起きた場所」で読ませる

ログは「いま起きたこと」なので、それを引き起こした場面のまま読ませないと順序が入れ替わる。
実際に2箇所で入れ替わっていた。

- 犬を埋めた話が、**山猫軒を見つけた場面**で流れる
- 服を脱いだ話が、**すでに脱いだ姿**の上で流れる

見た目を変える前に、ログを読ませて待つ。

```
選択 → ログを送る（前の場面のまま）→ 押す → 場面を変える → 本文を送る
```

`overlay.holdForLog()` が「ログの最後まで読んだら解決する約束」を返し、
`main.js` がそれを待ってから暗転／建て替えを始める。

**待たせるのは3つの場合だけ。**

| 変わるもの | 待つ | 理由 |
|---|---|---|
| 場所（暗転を挟む） | ○ | 起きた場所で読ませる |
| 役者の見た目（服装・鉄砲・相方） | ○ | 「脱いだ」と読む前に脱いでいてはいけない |
| カメラ（寄る） | **×** | 「調べる」は**寄ってから読む**のが正しい順序 |

★止めているあいだ選択肢は出さない。次の場面のものなので、いま押されては困る。
▼ だけを出して、押されたら場面を変える。

★止めないのは3つ。**ログが無いとき／既読で早送りするとき／自動検証のとき。**
既読の文で毎回止めると、2周目に押す回数がただ増える。

### 11.1.10 退室の歩き

**扉をくぐらせない。** `common/door_frame.png` は**閉じた扉**
（ノブ付きの木の扉。中央の暗い部分はガラスであって開口ではない）。
以前は扉の位置まで進めたあと、さらに奥へ押し込んで縮めていたので、
閉じた扉に突っ込んで見えていた。

**扉の 1.5 手前で止めて、一拍置く。** 通り抜けは暗転が引き受ける。
扉の音（`door`）はその一拍で鳴るので、開けて出ていったように読める。
扉際まで寄せると板が扉の絵に重なり、今度は「めり込んでいる」ように見える。

#### 二人をずらす向きは「画面の横」

同じ座標に板が重なると絵が二重に描かれて濁る。
★ずらす向きが要点で、**単に x をずらしても画面の奥行き方向にずれる**
（カメラが方位40度から見ているため）。手前の一人が奥の一人を隠すだけになる。

視線に垂直な水平線 —— `(cos40°, 0, -sin40°)` —— に沿ってずらす。
主人公が画面左、相方が画面右。普段の並びと同じになる。

#### 復路に「奥へ縮める」を掛けない

往路の処理をそのまま使い回していたので、**手前へ歩いたあと奥へ引き戻されていた。**
復路は手前へ出したらそのまま。画面の外へ出るのは暗転が引き受ける。

### 11.2 requestAnimationFrame を使う演出には必ず時間切れの保険を付ける

**rAF はタブが隠れると止まる。** 歩きや文字送りの途中で別のタブに移られると、
そこで止まったまま戻らず、ゲームが進まなくなる。
`walkActors` と `typewriter` はどちらも想定所要時間の倍で強制終了する。

## 12. 周回（Phase 5）

### 12.1 空腹は数値ではなく脈で見せる

`H` を画面に出さない（仕様書 §11）。周縁の暗さだけで伝えていたが、
暗いだけでは「そういう画作り」に見えてしまい、自分が弱っている感じにならない。
**心拍のような二拍の脈**と、周期をずらした横揺れを重ねる。

```
段階   0     1     2     3     4
濃さ   0    0.38  0.54  0.68  0.82   （脈の山で最大 0.97 まで振れる）
周期   —    3.4s  2.9s  2.3s  1.7s   （弱るほど速い）
```

★基準の濃さは上限より低く取る。上限に張り付くと脈が消える（実測して 0.82 に下げた）。

★毎フレーム書き換えるのは `opacity` と `transform` だけにする。
`box-shadow` や `background` を毎フレーム書くと画面全体の再描画になる。
暗くなり始める半径（`--vig-in`）は段階が変わったときだけ書く。

段階の移動自体もなめらかにする（指数で寄せる）。切り替わりが見えると演出ではなく表示になる。

### 12.2 既読の早送り

鍵は **場面番号＋文面のハッシュ**（`progress.textKey()`）。
場面番号だけでは足りない。同じ場面でも、選んだ道によって文面が変わるので
（相方が折れているか、隠したか）、読んでいない文を既読にしてしまう。

既読は「送らない」だけでなく**ページ送りもしない**。
1ページ目だけ即座に出しても、続きを出すために押す手間が残る。
全ページまとめて出し、選択肢もすぐ出す。

★**判断の場面は既読でも送る**（`game.js` の `NO_SKIP`）。
判断の重さは「読むのにかかる時間」で作っている。
決断の文が一瞬で出ると、選択がボタンを押す作業に落ちる。
短縮するのは部屋の描写と「調べる」だけ。

記録するのは**送り終わった時点**。表示した時点で記録すると、
途中で別の選択に飛んだ文を「読んだ」ことにしてしまう。

### 12.2.1 テキスト枠の寸法（実測で決めたもの）

| | 値 | 理由 |
|---|---|---|
| 通常 | 34%（下限 `--line`×6.2） | 42% では絵が隠れすぎた |
| 結末 | 40%（下限 `--line`×9） | 本文と到達記録が同居する。32% では本文が2行を切っていた |
| 鍵穴の一枚絵 | 25%（下限 `--line`×5） | 眼玉を潰さない |
| `PANEL_COVER` | 0.40 | 枠 34% ＋ 下の余白 3%。寄りの構図がこの上に収まる |
| 本文領域の下限 | `--line`×2 ＋ 字×0.35 | 削られる順番は「本文が最後」。段落の余白ぶんを足す |

枠が持つのは**本文と到達記録だけ**である。所持品と選択肢は枠の外に出した（後述）。

#### ★所持品と選択肢は枠の外に置く（枠のすぐ上）

**固定の高さの箱に「本文・所持品・選択肢」を同居させてはいけない。**

枠の高さは固定（絵を隠さないため）だが、中身の行数は画面の大きさで変わる。
字には下限があるので、画面が小さいほどチップもボタンも相対的に大きくなり、
固定の箱に入らなくなる。入らなかったぶんは必ずどちらかの形で表に出た。

- 本文が切られる（実機 iPhone 12 mini・667×375 で2行目の下半分が消え、ボタンと重なって見えた）
- ボタンがフレームの外へ出て押せない（重い場面で 667px 幅でも 4px はみ出す）

**枠の高さを場面ごとに測って合わせる方向は行き止まりである。** 実測すると必要な高さは
画面幅で 123px〜188px まで動き、しかも折り返しの段数が増える境目で跳ねる。
定数で追いかけるかぎり、画面の形が変わるたびに同じ不具合が出る。

場所を取り合わせないのが答え。`#overlay` の直下に `.controls` を置き、
所持品と選択肢をそこへ移す。`#overlay` は下寄せの縦並びなので、
**操作の段は必要な行数だけ上へ伸び、枠は本文だけを持って高さを固定できる。**

```
#overlay（縦並び・下寄せ）
  .controls   ← 所持品・選択肢。必要な行数だけ上へ伸びる
  .panel      ← 本文だけ。高さ固定（34% / 結末 40% / 鍵穴 25%）
```

実装で必要だったこと。

- `.controls` は `pointer-events: none`、中のボタンだけ `auto`。
  段そのものがタップを飲むと、ボタンの隙間を押しても文が送れなくなる
- 畳んだとき（▾ / H キー）に操作の段も消す必要がある。CSS は後ろの兄弟から
  前の兄弟を選べないので、`applySize()` が `#overlay` にも `data-size` を書く。
  `:has()` に頼らないのは、これが**演出ではなく操作の可否**に関わるため
- 空の `.chips` / `.choices` は `:empty` で消す。中身が無くても `gap` のぶん空く

実測（所持品6個＋選択肢4つ＝どちらも最大）。

| フレーム | 操作の段の上端 | 段の高さ | 枠 | 判定 |
|---|---|---|---|---|
| 1200×675 | 317px | 83px | 34% | 収まる |
| 667×375（12 mini 横） | 156px | 63px | 34% | 収まる |
| 569×320 | 109px | 63px | 34% | 収まる |
| 375×211（12 mini 縦） | −34px | 102px | 34% | 上へあふれる（縦持ちは要件外） |

副産物として結末の本文が広くなった。ボタン2つ（約42px）が枠から出たので、
667×375 の結末で本文が 2.6行 → 4.7行 になった。

#### ★本文2行の下限は段落の余白を足す

`.panel-text` の下限を `--line`×2 にしていたが、`.panel p` には `margin: 0.1em` がある。
隣り合う段落では上下が相殺されるので、**2段落の実寸は `--line`×2 ＋ 字の大きさ×0.3。**
この 0.3 を落としていたため、**2行保証は一度も成立していなかった。**
実機で2行目の下 3.4px が切れ、その真下のボタンと重なって見えていた。

```css
min-height: calc(var(--line) * 2 + var(--text-fs) * 0.35);
```

#### ★UI の寸法は `vw` ではなくフレームの幅（`--fw`）で決める

`#frame` は 16:9 固定なので、窓の形が変わってもフレームの縦横比は変わらない。
変わるのは実寸だけ。ところが字とボタンを `vw`（＝窓の幅）で決めていたため、
**横長で背の低い窓ではフレームが小さいのに字とボタンだけが大きいまま**になり、
高さ 34% の枠をボタンが占領して本文が1行も入らなくなっていた。

`#frame` に `--fw`（フレームの幅）と `--line`（本文1行の高さ）を持たせ、
枠の中の寸法をすべてこれに比例させる。こうすると**枠に何行入るかが窓の大きさに依らず一定**になる。
実測（本文＋ボタン2つの通常画面）: `--fw` 1600px→8.4行 / 1072px→5.6行 / 640px→2.7行 / 420px→2.0行。

#### ★結末の到達記録は `display` ではなく `visibility` で出す

`paginate()` は本文の枠を実測して区切るが、到達記録の箱は最後のページで初めて
`display:block` になっていた。**区切りを決めた時点では存在しない**ので、
最後のページだけ箱のぶん（約2行）場所が足りず、結末の文が1行半に潰れていた。
最初から場所を取っておけば区切りが正しく決まり、枠の高さも途中で動かない。

### 12.2.2 ★ページの区切りは「行数」ではなく高さで測る

行数で数えていたので、**長い行が折り返したぶんを勘定できなかった。**
「看板。「どなたもどうかお入りください。決してご遠慮はありません」」は
1行として数えていたが、画面では2行になる。結果、1ページ目からスクロールが必要になっていた。

段落を一度すべて出して `offsetTop` の差で送りを測り、枠の高さに収まるところで切る。
`offsetHeight` では余白が入らないので、必ず差分で取る。

これで**枠の高さ・字の大きさ・行間・画面幅のどれが変わっても追従する。**
調整用の定数（旧 `PAGE_WEIGHT`）は不要になった。

区切る前に**選択肢と枠の大きさを確定させる**こと。選択肢が2段に折り返すと
本文の領域が縮むので、先に区切ると入りきらないページができる。

### 12.2.3 塊の区切り線は隣接セレクタで付けない

`.log + .body` で余白と罫線を付けていたが、**前の塊を `display:none` にしても
隣接は成立する**ので、中身が無いのに余白と罫線だけが残り、本文が下へ押し出されて
スクロールが必要になっていた（59px の空白が空いていた）。
見えている塊にだけ JS で `sep` を付ける。

### 12.2.4 据え置きの本文は、新しいログがあるなら持ち込まない

同じ部屋で「調べる」を選ぶと、看板の文面（据え置き）＋ 調べた文（新しい）で
枠（3行）を超え、上の行が半分に切れていた。**新しいログがあるときは本文を出さない。**
看板の文面は壁の板に描いてあるし、「看板の前に立つ」でもう一度出るので読み返せる。

ログが無いとき（小物の入れ替えなど）は、本文しか出すものがないので残す。

### 12.2.5 場面の見出しは本文に混ぜない

「——廊下」のような見出しを本文の1行として流していたので、
ページ送りで下に流れて**「どこにいるか」が画面から消えていた。**
`view()` が `head` として別に返し、枠の上の段に据え置きにする
（送らない・ページに数えない）。

副産物として、部屋の本文が2ページから1ページに収まるようになった（押す回数が1回減る）。

#### 枠の中で伸び縮みするのは本文だけにする

`.panel-bar` に `flex: 0 0 auto` を付けていなかったので、文章の多いページでは
この段が flex に潰され、中の相方の肖像（高さ固定）が段からあふれて本文に重なっていた。
潰れる量は文章の量で変わるので、**枠の高さは固定なのに「内容でサイズが変わる」ように見えていた。**
本文（`.panel-text`）だけを `flex: 1 1 auto; min-height: 0` にし、他は全部 `flex: 0 0 auto` にする。

#### 相方の肖像は絶対配置する。基準は「操作の段の上」

流れの中に置くと、出たときだけ他の位置がずれる。喋ったときだけ出るものなので、
出入りで他が動いてはいけない（**ボタンが動けば押し間違いになる**）。

★基準は `.controls`（操作の段）の上である。`.panel` の上ではない。
枠の上に置いていたが、選択肢を枠の外へ出した結果、**肖像とボタンが同じ場所を
取り合って重なった**（実機 560×315 の S03 で確認）。段の上に積めば、
選択肢が何段になっても肖像はその上へ逃げる。

`.panel` / `.controls` の `overflow` は `visible` のままにしておくこと（`hidden` だと肖像が切れる）。
`.controls > :empty { display: none }` のような一括指定も禁止。肖像は絵の読み込み前に
一瞬空になるので、まとめて消すと顔が出なくなる。対象は `.chips` と `.choices` に絞る。

実測（560×315・所持品6個＋選択肢4つ＝最大）: 肖像の上端は枠上端から 16px。
ボタン・チップ・枠との重なりはいずれも 0。

#### 文字を隠せるようにする

絵を見たいときに文字が邪魔になる。切り替えは**「出す／隠す」の2つだけ**にする
（3段階だと全部隠すまでに2回押すことになり、「絵を見たい」に対して遠い）。
ボタンのほかに **H キー**でも切り替える。中間の小さい枠は、
鍵穴の一枚絵のときだけ自動で使う。

### 12.3 タイトル画面

背景に専用の絵を用意しない。**山道の最後のカット（山猫軒の発見）をそのまま使う。**
「どなたもどうかお入りください」の札が立っている画がタイトルなので、
押した瞬間から店の招きに応じたことになる。アセットは1枚も増えない。

題字は下寄せにする。中央寄せにすると札に重なる（実機で並べて決めた）。
札が上、題字が下に来ると「招きに応じて中へ」の順に読める。

`createUI(root, hooks, { defer: true })` で最初の描画を止めておき、
「店に入る」で `begin()` する。タイトルを出すとき `prevPlace` を `'TITLE'` にして、
最初の場面が必ず暗転を挟むようにする（ここを空にすると画面が飛ぶ）。

到達記録はタイトルに置く。周回の起点と、集めたものを見る場所を同じにする。
「記録を消す」は `confirm()` を使わない二段確認にする
（ブラウザのモーダルは他の入力を全部止めてしまう）。

## 13. 音

出典は `src/data/audio.js`。**どの場面で何が鳴るかは純粋関数**（`bgmFor` / `seForChoice` /
`seForScene`）に置く。`ui/audio.js` が持つのは「どう鳴らすか」だけ。依存の向きは他と同じ。

### 13.1 BGM と SE で実装を分ける理由は容量

| | 実装 | 理由 |
|---|---|---|
| BGM | `<audio>` | 6曲を WebAudio でデコードすると 300MB 級になる。流すだけなら要らない |
| SE | WebAudio | 短いので展開しても軽い。重ねて鳴らせて、押した瞬間に鳴る |

### 13.2 素材の音量差はコードで吸収する

無料素材は音量が揃っていない。実測で **RMS に 20dB の開き**があった
（`select` -31.1dB / `eyes` -10.4dB）。同じ音量で鳴らすと、決定音は聞こえず
眼玉は割れる。

★**波形を書き換えない。** 鳴らすときに `gain` を掛ける。
素材を差し替えても `data/audio.js` の数字を直すだけで済む。
`select` は頭に 0.09秒の無音があったので `offset` で飛ばしている
——押した瞬間に遅れて聞こえると、反応が悪いと感じる。

実測は `docs/音源集.md` と `data/audio.js` のコメントに残してある。

### 13.3 鳴らし始めは利用者の操作を待つ

ブラウザは利用者の操作なしに音を鳴らせない。
**タイトルの「店に入る」を解禁点にする。** ちょうど良い位置にボタンがある。

### 13.4 音量の補間を requestAnimationFrame に乗せない

rAF はタブが背面に回ると止まる。曲の切り替えを rAF で補間していたら、
**背面のタブで音量が 0.03 のまま固まった。**
`setInterval` と時計の差分で自分で回す（§11.2 と同じ考え方）。

### 13.5 同じ曲は切らない

`playBgm(id)` は同じ id なら何もしない。往路の5室で曲が切れると台無しになる。
曲が変わるのは **山道 → 往路 → 反転 → 復路 → 結末** の5回だけ。

### 13.6 音が無くても遊べること

画像と同じ。ファイルが無ければ黙るだけで、進行は一切止めない。

---

### 13.7 音量は5段階の点で決める

滑り子（スライダー）にしない。**細かく決められても、細かく決めたい人はいない。**
押した回数で分かるほうが速く、指でも狙いやすい。

段階は `消音 / 小 / 中 / 大 / 最大`。値は耳で等間隔に感じるように取ってある
（`0 / 0.15 / 0.35 / 0.62 / 1.0`。等差にすると小さい側が効かない）。

開く場所はタイトルと本編の2つだが、作るものは1つ（`ui/settings.js`）。
保存は進捗と**別の鍵**（`demo8.audio.v1`）——「記録を消す」で音量まで消さない。
